# mlarena-sdk — Python SDK

**Purpose**: Python client (`mlarena-sdk` 4.23.0, import `mlarena`) and the `mlarena` command over the public backend REST routes (`/api/*`).

**Key features**:
- Bearer-token auth with scope-segmented keys `mlk_<scope>_<lookup>_<secret>` (`user`, `author`; a `creator` / `teacher` key is an `author` key), or, in a GitHub Actions job, the 15-minute `mlo_<lookup>_<secret>` token of the OIDC exchange (no stored secret).
- One method per backend route, plus client-side compositions (`submit`, `status`, `tail_logs`, `resolve_runtime`, `download_dataset`, `download_replay`, `chat`, `check`, `create_challenge_for_class`, `use_example_challenge`, `start_from_example_course`) that add no endpoint.
- The `mlarena` command (`whoami`, `submit`, `challenge push`, `course push`, `course export`): the same methods from a shell or a workflow.
- Reads the backend's names as served (snake_case `LeaderboardRow`, `RunResult`, the submission status block); keeps no status set or key map of its own.
- Deprecated Python names from before the challenge/submission rename still resolve (published client).

**Links**: [`../ARCHITECTURE.md`](../ARCHITECTURE.md) · [`../backend/PROCESS.md`](../backend/PROCESS.md) (route groups, schemas) · [`../frontend/PROCESS.md`](../frontend/PROCESS.md) (peer consumer) · [`../CLAUDE.md`](../CLAUDE.md) (parity rule) · parity gaps: "Parity gaps" below

## Parity rule

The SDK and the React console are peers over one REST surface; every user-facing workflow is reachable from both.
- No `/api/sdk/*`, no SDK-only or frontend-only route. A route change updates `mlarena/client.py` and `frontend/src/services/*` (+ hook) in the same change.
- Auth is the only divergence: session cookie (console) vs bearer token (SDK). Route, payload and response never branch on the caller.
- SDK ergonomics are compositions of public routes, never new endpoints.

### Parity gaps

Console-only (a route the console calls, no SDK method):
- The public overview markdown / miniature reads (`GET /api/challenge_asset/*`) have no participant method; a challenge's staff read them through `challenge_markdown` / `challenge_image`, and its configuration as `creator_challenge()["configuration"]`.
- The env-runtime image list (`GET /api/docker-kernel-version/`, the picker behind `update_settings(docker_image_env_runtime_id=…)`) has no method: the route takes `AdminUser` (`backend/app/core/auth.py`), a signed-in admin session, never a key, so an SDK method would only raise 403.
- `workspace()` has no `scope` parameter: `GET /api/author/workspace?scope=all` (every challenge and course, for an admin) calls `require_admin_session`, which refuses every key.
- By design: admin cluster-ops (machines and their queues and grants, maintenance, data-quality, admin runs, tag CRUD), the admin challenge delete (`DELETE /api/challenges/<id>`, listed in the platform CLAUDE.md), and **API-key management**: `GET /api/auth/api_keys` and `POST /api/auth/api_keys/{scope}/rotate` take `SessionOnlyUser` and answer 403 to a bearer caller, so that a leaked `mlk_user_…` key cannot mint a `mlk_author_…` one for the same account; `me()` covers "who am I", keys are rotated from the console's Profile page. This is the auth axis of the parity rule.

- The credits that staff read on a course or a challenge (`credit_usage(course_id=…)` / `(challenge_id=…)`) and a run's `credits` are served to both; the admin side of credits (Admin › Users, grants, a machine's rate, the `credits_enforced` switch) is admin cluster-ops, console-only.

SDK-only: none. Every other participant and author route has its method (table above) and its console screen.

## Contracts

- **Runtime** (`../modelmanager/PROCESS.md` "Machines and queues") — `update_settings` carries `machine_id`, the nine sizing keys (K8s quantity strings), `number_of_agents`, and the admin-only `env_gpu_count`, `agent_gpu_count`, `gpu_memory_limit` (`_UNSET` sentinel: `None` sends null), `docker_image_env_runtime_id`. `engine_id` raises `TypeError`. `machines(kernel_version=None)` returns `MachineOut` rows as served.
- **Agent runtimes** (`../modelmanager/PROCESS.md` "Challenges") — a code challenge offers a set of agent runtime images and names a default: `update_settings(agent_runtime_ids=[…], default_agent_runtime_id=…)` (author keys, running-editable; 400 on a foreign-kernel id, an empty set or a default outside the set), read back as `challenge()["runtime_options"]` / `["default_agent_runtime_id"]`. Each runtime has a `name`, distinct on a challenge: `submit(..., runtime="sklearn")` resolves it client-side through `resolve_runtime(cid, name)` over `runtime_options` (no route takes a name). `agent_runtimes(kernel_version)` is the catalogue the set is picked from (author scope). `set_agent_runtime` outside the set is a 400; a deploy of a submission whose runtime left the set is a 409.
- **Challenge config** (the platform's `modelmanager/PROCESS.md` "Challenge config") — one flat document, every key the column's name = the `update_settings` keyword = the `challenge.toml` key (`config_fields()`). Two editors: `update_settings` and `challenge.toml` (applied on `upload_env_file` / `update_env_file_content` / `push_challenge` / `import_challenge_from_github`, all or nothing, errors naming lines). One owner per key: a file-owned key is a 400 from `update_settings`. `creator_challenge()["config"]` = `{values, origin, file_lines, file_applied_at_ts, file_in_sync}`. `env_max_time_per_step_second` is gone (4.3.0).
- **Data feed** — `update_settings` carries the admin-only `data_source_*` + `batch_cron` keywords (sentinel `_UNSET` = not sent, `None` = null; `data_source_filter` is `dict[str, str]`); the backend answers 403 to a non-admin. The SDK reads no feed.
- **Payload keys are the backend's exactly** (request schemas are `extra="forbid"`): e.g. `submission_name`, `copy_from_submission_id`, `copy_from_challenge_id`, `max_active_submissions_per_participant`, `challenge_id`; chat `charter_accepted`, `content`, `reason`, `llm_base_url`, `llm_model`, `llm_api_key`, `turn_timeout_sec`, `max_turns_per_session`, `max_sessions_per_participant`, `max_concurrent_turns`.
- **Submission status block** — every reply carrying a submission's `status` carries `SubmissionStatusFields` (`backend/app/views/submissions/_schemas.py`): `status`, `phase`, `last_status_message`, `status_update_ts`, `is_uploadable`, `is_deployable`, `is_settled`. `status` ∈ `SubmissionStatus` (`modelmanager/modelmanager/submissions.py`): `created`, `upload_failed`, `upload_validated`, `deploy_queue`, `deploy_run`, `deploy_failed`, `active`, `deleted`. The SDK gates on the served flags: `tail_logs` stops on `is_settled`; `submit` deploys only when `is_deployable` and returns `{"submission_id", "deploy"}`; `submit(wait=True)` returns an `active` submission or raises `SubmissionError`. `/submissions/mine` serves no `deleted` rows.
- **The submission** — `submission(sid)` is `SubmissionOut` (`backend/app/views/submissions/_schemas.py`): the status block + `id`, `challenge_id`, `submission_name`, `created_at_ts`, `is_public`, `owner`, `team`, `viewer_role` (`owner` | `teammate` | `staff` | `public`), `agent_runtime`, `latest_deploy` (`DeployOut`, None before the first deploy), `queue_info`, the `LeaderboardRow` numbers (`score`, `score_ci95`, `metrics`, `metrics_window`, `number_of_runs`, `last_end_run_ts`, `action_time_max_sec`, `agent_metric_*_max_bytes`) and `latest_run_failure`. Every reader reads it and its `runs` / `deploys` / files; only the owner writes (`update_submission`, uploads, deploy, delete). `tail_logs` and `submit` poll it, and `tail_logs` reads the latest attempt's runs with `submission_runs(sid, deploy_id=latest_deploy["id"])`. `list_submission_files` is metadata (`name`, `size`, `role` ∈ `entry` | `report` | `other`, `language`); a report is a `README.md` (any case) or a `.pdf`, uploaded like any file. `delete_submission` on a chat_v1 challenge is a 409.
- **Run model** — `submission_runs()["runs"]` rows are the backend's `RunResult` (`backend/app/views/run_serializers.py`): run columns (`job_status`, `job_error_type`, `job_error_message`, `credits` — `{amount, seconds, kind, resource}` for the challenge's staff, else null —, `job_retry_count`, `submission_deploy_id`, `env_nb_steps`, `env_error_type`, `env_error_message`, env metrics) + `submission_results` (one `RunSubmissionResult` per agent: `submission_id`, `submission_status`, the per-run columns `score`, `score_variance`, `n_episodes`, `score_ci95`, `metrics` (env keys + optional `score2`), `agent_nb_steps`, `game_outcome` (null on a solo run), `agent_error_type`, `agent_error_message`, `agent_stdout_logs`, and the footprint `agent_busy_time_sec`, `agent_call_count`, `agent_call_time_total_sec`, `agent_metric_cpu_time_total_sec`, `agent_metric_ram_gib_sec`, `agent_metric_gpu_energy_j`, `agent_metric_gpu_busy_sec`, `agent_metric_vram_max_bytes`, `agent_energy_wh`, `agent_co2e_g`; the run's env side `env_metric_ram_gib_sec`, `env_metric_gpu_energy_j`, `env_metric_gpu_busy_sec`, `env_energy_wh`, `env_co2e_g`). A null footprint value = the run was not metered; nothing in the SDK reads them as numbers. `env_error_type` / `agent_error_type` ∈ `RunErrorType` (`code_error`, `timeout`, `oom_killed`, `crash`, legacy `simulation_error`, `pod_crash`). The caller finds its own row by `submission_id`; `env_*` diagnostics are null on participant routes, `job_error_message` is served to the challenge's staff only. `latest_deploy` carries `failure_owner` (`participant` | `challenge` | `platform`). Every run row carries `replay` (`ReplayOut`: `render_format` ∈ `frames_v2` | `video_mp4` | `image_png`, `signed_url`, `render_size_bytes`; None without a replay); `replays()` / `replay()` rows are the public `ReplayRun` instead (`simulation_result_id`, `created_at_ts`, `env_nb_steps`, `replay`, `submission_results` limited to `id`, `submission_id`, `submission_name`, `user_name`, `agent_attached_player_id`, `env_player_name`, `score`, `game_outcome`, `final_rank`: the same keys, no metrics or diagnostics); `submission_runs()` and `replays()` carry `challenge_context` = `RunsContext` (`metrics`, `number_of_agents`, `render_delay_second`, the default frame duration). `download_replay` names the file `<simulation_result_id>` + the format's key suffix (`.experiment.mp`, `.frames.mp`, `.mp4`, `.png`). `run_benchmark` returns the challenge's latest benchmark run in the same shape (with the env diagnostics); `benchmark_status` returns `{run, checks}` (`run` None before the first run, `checks` the config's budgets against the completed run); the backend scores the benchmark submission when the run completes.
- **Kinds** — `available_kinds()` rows carry `kernel_version` (the name every payload uses, `creator_challenge()["configuration"]` and the `challenge` of `workspace()` rows included) and closed `capabilities`: `agent_template`, `benchmark`, `env_structural_check`, `runs`, `chat`, `submission_upload`, `submission_filename`, `elo`, `episode_budget_brackets`, `run_limits`, `agent_containers`, `multi_agent`, `exercises`, `leaderboard` (False on exercise_v1: its board is hidden); plus `has_machine`, `runtime_defaults` and `runtime_presets`. The settings flags say which `update_settings` keywords a kind accepts; the backend answers 400 to the others.
- **Errors** — every refusal goes through `_handle_response` (401/403/404) or `_failed` (other codes) and carries `status_code` + `body`; no API call ends on `requests.raise_for_status()` (the presigned-R2 fetch in `download_dataset` is the one exception, pinned by `test_no_api_call_ends_on_raise_for_status`; `download_replay` raises `MLArenaError` with the storage's status code). A deploy 409 body carries `deployment_limits`, `active_submission_limits` and `reason` (always there: null on a quota refusal, `out_of_credits` otherwise). A refusal with a cause a program may act on names it in `body["reason"]`, beside `error`; the SDK maps one to a class (`enrollment_required` → `EnrollmentRequiredError`) and passes the others through, documented on `MLArenaError`: `terms_required` (403, see "Terms" below), `out_of_credits` (409: the challenge's owner has no credits left, `backend/app/services/credit_refusals.py`; on `deploy_submission` beside the two quota blocks, on `open_chat_session`, `send_chat_message`, `submit_exercise`, `run_benchmark`, `clean_redeploy_submission`, `clean_redeploy_all` and the writes of a started challenge's files; the start gate serves it as a `start_blockers` code and a chat session as `can_send_reason`, with no `reason` key), `files_unreadable` (503).
- **Score model** (`../modelmanager/PROCESS.md` "Score model") — a challenge's declaration is `metrics: [MetricSpec]` (+ `window_days`), plain dicts with the ten keys `key, label, source, agg, order, format, unit, precision, is_ranking, visible` (`format` ∈ `metrics_schema.FORMATS`, `energy` / `mass` with a null `unit`; the platform keys add the footprint `energy`, `co2e`, `cpu_time`, `gpu_time`, `busy_time`, refused off flex_v1; the server validates, the SDK only documents them and formats them in `format_metric`); a submission's values are `score` + `metrics` (`{key: value}`) (+ `metrics_window`). `update_settings(metrics=…, window_days=…)` sends the whole list (`window_days=None` sends null and removes the window, `_UNSET` sentinel); the six pre-4.0.0 keywords (`metric`, `metric2`, `is_elo_score`, `metric_order`, `frontend_precision`, `metrics_schema`) raise `TypeError` naming `metrics` (`_refuses_removed_score_kwargs`, D5 — no alias). Course payloads carry `metric` (the ranking MetricSpec) + `value`.
- **Footprint** — `challenge_footprint(cid)` returns `ChallengeFootprint` as served: `{last_30d, since_start}`, each `{runs, metered_runs, agent_energy_wh, env_energy_wh, agent_co2e_g, env_co2e_g}` (Wh, g).
- **Leaderboard** — `leaderboard(challenge_id=None, top=None, *, aggregate=None, me=False, q=None, window=None, offset=None, around=None)` sends only the passed keys (`limit`, `offset`, `aggregate`, `me`, `around`, `q`, `window`); one board per challenge, a course challenge's being its class (`course_context`, `passed`); without `aggregate` the backend serves its default `user` (one row per participant), as the console asks for. The backend serves one `LeaderboardEnvelope` (`backend/app/views/_schemas.py`); the method returns its `leaders` as a DataFrame of `LeaderboardRow` with every other key (`challenge`, `total`, `me`, `around`, `matches`, `course_context`) on `df.attrs`, or the envelope dict as served without pandas. In the DataFrame (`_leaderboard_records`) each row's `metrics` becomes one column per declared key and, when `challenge.window_days` is set, `metrics_window` one `metrics_window_<key>` column per key; `df.attrs["metrics"]` is the declaration. A declared key equal to a row column raises `MLArenaError`. On a course challenge whose course the caller is not a member of (not enrolled, not its owner, an assistant or an admin), `course_context["names_withheld"]` is true: the rows keep every key, with `username`, `avatar_key`, `submission_id`, `submission_name`, `team_id`, `team_name`, `team_members`, `datagouv_reuse`, `created_at_ts`, `last_end_run_ts`, `number_of_runs`, `action_time_max_sec`, `agent_metric_total_ram_max_bytes` and `agent_metric_vram_max_bytes` None and `can_open` False, and the backend refuses `q` and `around` (`MLArenaError`, 400). That is a public course: a private course's challenges are its members' only (404). An exercise set's board is served to its course's staff only (404 otherwise). The SDK passes both through unchanged.
- **Chat challenges** (`chat_v1`) — no upload/deploy; the team's submission is created by the first `open_chat_session` (born `active`; `create_submission` answers 409). The agent sleeps after 30 idle minutes and a read of `chat_challenge` wakes it: `wait_for_chat_agent` polls that read until `agent_online`, and `chat().say()` calls it before `open_chat_session` (which answers 409 while the agent is not online). `send_chat_message(wait=True)` sends (202 `{"turn", "message"}`) and polls `chat_session` every 0.7 s until that turn is `completed` or `failed`; its `timeout` restarts whenever the pending turn's `queue_position` (served, never derived) goes down. Money is served as two-decimal strings; only `ChatConversation.total_amount_eur` parses a `Decimal`. The group's cumulative euros and per-rule scoreboard are `participant.total_amount_eur` / `participant.scoreboard` on both the challenge view and the session view. `update_chat_settings` sends only the keywords passed (`None` clears a limit, `llm_api_key=""` clears the key; the key is never read back, only `llm_api_key_set`).
- **Exercise challenges** (`exercise_v1`) — no upload/deploy; the group's submission is created by the first attempt (born `active`; `create_submission` answers 409). `submit_exercise` sends `CreateExerciseAttemptRequest` with both keys (`code` / `answer`, the unused one null; exactly one checked client-side before any request), answers 202, and with `wait=True` polls `exercise_attempt` every 0.4 s (the console's cadence) until `passed` / `failed` (returned) or `error` (raised, attempt in `.body`); the timeout raises with the last attempt in `.body`. A 404 is `ChallengeNotFoundError` on challenge routes and `ExerciseAttemptNotFoundError` on `/attempts/{aid}`. The four limits (`time_limit_sec`, `memory_limit_mb`, `max_concurrent_attempts`, `max_attempts_per_minute`) are config keys of `update_settings` (capability `exercises`). `check()` sends `source_of(obj)` and prints `format_attempt`.
- **Course challenges** (docs/course_challenges.md §6.9, §7.5) — a challenge belongs to one course: `add_course_challenge(course_id, name=None, *, kernel_version=None, copy_from_challenge_id=None, module_id=None, pass_threshold=_UNSET)` sends exactly one of `kernel_version` / `copy_from_challenge_id` (`TypeError` otherwise, and on an int in place of `name`, the pre-4.23 linking call); `pass_threshold` left out lets the kind decide, `None` sends null. `update_course_challenge(module_id, challenge_id, /, **fields)` takes `pass_threshold` and `module_id` as the route's body keys (the positional `module_id` is the path, positional-only so the body key keeps its name). `create_challenge` makes a competition (the publishing right). The methods of the removed routes went in 4.23.0 (`create_module`, `list_modules`, `fork_module`, `link_module`, `unlink_module`, `attach_challenge`, `detach_challenge`, `update_challenge_link`, `add_course_exercise_set`, `remove_course_challenge`, `challenges_for_course`, `copyable_challenges`, `challenge_courses`, `use_challenge_with_class`; `leaderboard(course_id=)`, `list_courses(challenge_id=)`, `mark_lesson_*(course_id=)`, `delete_module(force=)`, the module `visibility`); a removed route answers 410 with the sentence that names its replacement, which `_failed` puts in the message.
- **Terms** (`backend/app/services/terms.py`) — an account accepts the terms of use once, before its first challenge: `accept_terms()` (`POST /api/auth/terms/accept`, no body; an `author` key, the account's holder: a `user` key and an `mlo_` token are a 403), read back as `me()["terms_accepted_at_ts"]`. Until then the four routes that create a challenge (`add_course_challenge`, `create_challenge`, and `copy_module_into_course` / `duplicate_course` when a challenge would be copied) answer 403 `{"error", "reason": "terms_required"}` and create nothing. `_handle_response` raises it as `PermissionDeniedError` with the server's body and a message that adds the page of the terms (`<base_url>/terms`) and `client.accept_terms()`; under a GitHub Actions credential the message says the account's holder accepts (console or key). The SDK never calls `accept_terms` itself. `create_challenge_for_class` and `use_example_challenge` into a new course would create a course before the refused challenge: they read `me()` first (`_refuse_without_terms`) and raise the same error (class, status, body: `TERMS_REQUIRED`, `TERMS_REQUIRED_REASON` mirror the backend's sentence and reason) before any write; a credential the platform does not know is left to the route's 401. `start_from_example_course` and `use_example_challenge` into an existing course are one route, which copies everything or nothing and alone knows whether a challenge would be created: its refusal is raised as it is. No CLI command creates a challenge (`challenge push` and `course push` write existing ones), so the CLI has no terms command; a refusal would print the client's message like any other.
- **One kind of author** (docs/course_challenges.md §6.10) — no account flag opens authoring: every staff member of a challenge writes its code and files, for the four kinds. A challenge reference (`ChallengeRef`) and `challenge()` carry `can_copy` (the rule of the copy routes: 404 where it is false). What bounds an account: `max_courses_limit` (10), and at Start the blockers `started_challenges_cap` (`max_started_challenges_limit`, 10 started course challenges that are not exercise sets) and `started_sets_cap` (15 exercise sets); admins exempt.
- **Credentials** (`ci_auth.py`) — one order for `connect()` and the CLI: `api_key` → `MLARENA_API_KEY` → GitHub Actions OIDC, when `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN` are both set. The exchange: `GET {request url}&audience=<audience>` with `Authorization: bearer <request token>` → `{"value": jwt}`, then `POST /api/auth/oidc/github` `{"token", "scope"}` → `{"access_token", "expires_at_ts", "username", "source_revision"}`. A 401 / 403 raises `AuthenticationError` / `PermissionDeniedError` whose message is the server's, unchanged. A key that is set but malformed raises; it is never a reason to try the next source. The client renews an exchanged token 60 s before `expires_at_ts` (`_headers`), so a `submit(wait=True)` may outlive it. CLI scopes: `submit` and `whoami` ask `user`, `challenge push`, `course push` and `course export` `author` (`OIDC_SCOPES`); `connect(scope="creator" | "teacher")` warns and asks for `author` (`LEGACY_OIDC_SCOPES`); an API key carries its own.
- **Bundles** — `push_challenge` / `push_course` send one multipart field `archive`: `make_bundle(dir)` (rooted at the directory; `.git`, `__pycache__`, `*.pyc`, `.DS_Store`, `.venv`, `node_modules`, `.ipynb_checkpoints` left out; a symbolic link raises), or an existing archive as it is. The server extracts, validates and applies; the client parses nothing but `course.slug` (the route's slug, when `slug=` is not given). `subpath` (CLI `--path`) is the folder inside the directory that holds the challenge or the course: for a directory both pushes bundle only that folder; for an archive `push_challenge` sends it as the route's `path` query and `push_course` raises (the course route takes none). `push_challenge` answers `ChallengeBundleResponse` (`message`, `dry_run`, `env_files`, `env_changed`, `overview_updated`, `agent_template_updated`, `image_updated`, `ignored`, `config`, `validation`, `source_revision`); `push_course` answers `CourseBundleResponse` (`dry_run`, `course`, `modules` with `lessons` / `challenges` / `orphaned_lessons` / `pruned_lessons` / `assets`, `unmanaged_modules`, `unmanaged_challenges`, `source_revision`, `url`, `warnings`); the course, each module and each lesson carry `action` and `changes` (the fields an `updated` or `adopted` item changed), `assets` carries the store keys `written_paths` / `removed_paths` (beside the `written` / `removed` counts, a server expand step kept for CLIs 4.16–4.21, which the CLI does not read). `_course_plan_lines` prints `lesson rag: updated (body_md, title)`, `challenge Maze: updated (module_id)`, one line per name of `unmanaged_challenges`, every `warnings` sentence (the unused manifest keys first) and `assets: 2 written (a.png, b.png), 37 removed (…) — files no lesson links`, each list cut at `PLAN_PATHS_SHOWN` names + "and N more". A 200 whose `validation.ok` is false is an applied bundle with a broken `env.py`: the CLI prints the errors and exits 1.
- **Same commit** — a submission created by an `mlo_` token records the run's commit (`submission()["source_revision"]`). `create_submission` sends `allow_same_commit` only when true; the second create of a commit is a 409 `SubmissionError` with `body["submission_id"]`. `submit` turns that 409 into `{"submission_id", "deploy": None, "already_submitted": True, "status": submission()}`; any other 409 propagates. `submit(deploy=False)` returns `{"submission_id", "deploy": None}` after the upload check.
- **submit checks first** — `submit` reads `challenge()` once before `create_submission` and refuses, with nothing created: a runtime name or id outside `runtime_options`, an `agent=` that is a path or an instance (a class or a module only; the class's `inspect.getsource` is the whole `agent.py`), `agent=` on a challenge whose `entry_filename` is not `agent.py`, a missing file, two files of one base name, more files than `max_upload_files` (a code challenge's template `agent.py` counted) or more bytes than `max_upload_size_bytes`. The server still validates. Every error raised after the create carries `MLArenaError.submission_id`; before the deploy is accepted the message also names it with the `deploy_submission` / `delete_submission` calls (`_left_behind`). Nothing is deleted.
- **Course manifest** — the format is the server's (`backend/app/services/course_manifest.py`): `course` (`name`, `slug`, `code`, `description`, `visibility`, `instructor_name`, `start_date`, `end_date`, `cover`) and `modules` (`title`, `slug`, `renamed_from`, `summary`, `icon`, `is_published`, `challenges` of `{slug | challenge_id, pass_threshold}` — a challenge of this course, placed in the module; a competition or another course's challenge is refused —, `lessons` of `{title, slug, renamed_from, kind, file | body_md, gated, is_published, estimated_minutes, children}`); a relative path is relative to the folder of the file that writes it (a manifest path from `course.yaml`, a lesson's link from the lesson file's folder, no `..`); unknown keys are refused, a module's `visibility` and an entry's `label` are warned and ignored, `course.visibility: unlisted` is refused; `competitions:` / `competition_id:` are permanent input aliases the server reads (CLAUDE.md, "Vocabulary"). The client parses none of it. `export_course_to_dir(slug, path, *, overwrite=False)` is `GET /api/academic_courses/{slug}/bundle` unpacked by `extract_bundle`: the server writes the folder (`course.yaml`, `<module>/<lesson>.md` with the files beside them, the cover; for the course's staff the template's `.github/workflows/push.yml` and a `README.md`), and the method returns the parsed `course.yaml`. The target must be missing or empty (checked before the request); `overwrite=True` (CLI `--overwrite`) writes the course's files over a folder's and keeps the rest, so a checkout keeps its `.git`. `mlarena course export SLUG [DIR]` (DIR default `./SLUG`) prints one line per module and the next step (`mlarena course push --dry-run DIR`).
- **Module assets** — a module has one asset store; a lesson body links a file by its path in it (`![](media/fig.png)`), resolved against `lesson()["asset_base_url"]`. `upload_module_asset` sends multipart `file` + form field `path` (default on the server: `media/<file name>`) and returns `{path, url}`; `list_module_assets` rows add `size_bytes`. A module with `content_origin == "bundle"` refuses editor writes (409) until `detach_module`.
- **Course payload names** — a course object carries `has_cover` (never the stored `cover_image_path`: the catalog and the landing are public reads and an NFS path would publish the share's layout) and the client builds the image URL from the course id (`course_cover` / `courseCoverUrl`); a module object is keyed `id` and carries its `course_id`, a course's module row is keyed `module_id` and a module's challenge row carries `challenge_id` / `challenge`; course payloads carry `single_challenge_id` (the course is shown as its one challenge: one module, one challenge, no lesson) and `example_listed_at_ts`; an enrollment row is keyed `user_id` and dated `enrolled_at_ts`; the enroll-info payload nests the course under `course`. A course's module row carries `layout` (`simple` | `advanced`) — the platform's own rule, not a client guess. `update_course` sends only the keywords passed and drops a `None`, except `end_date` (`_UNSET` sentinel): `end_date=None` sends `null`, which clears the end date.

## Deprecated aliases (frozen — CLAUDE.md, "Vocabulary")

- `_RENAMED_METHODS`: old method names (`competitions`, `create_competition`, `deploy_agent`, `agent_games`, `submission_games`, …) warn (`DeprecationWarning`, at the caller's line) and call the new method. An alias keeps its old signature, every parameter by position or by keyword: where the new method takes some by position only (`update_course_challenge(module_id, challenge_id, /, **fields)`), `_deprecated_alias` binds those names itself and passes them by position, so `update_competition_link(module_id=2, competition_id=42, pass_threshold=50)` works and its `module_id=` is the path's module. `test_an_alias_called_with_its_old_keywords_reaches_the_new_method` calls each alias with its old keywords (`_OLD_KEYWORD_CALLS`, one entry per alias). `_KEYED_BY_SUBMISSION_METHODS` (`agent_status`, `submission_status`, `submission_overview` → `submission`) do the same and drop the old leading `challenge_id`. The module raises at import if a target method is missing.
- `_LEGACY_KWARGS`: old keyword names (`competition_id`, `agent_id`, `agent_name`, …) are accepted on every public method for a parameter it takes by keyword (the two ids of `update_course_challenge`, new in 4.23.0, are positional only: its frozen alias takes the old keywords); passing both spellings raises `TypeError`.
- `_GONE_COMPETITION_METHODS` (`attach_competition`, `detach_competition`): their methods' routes are gone; they raise `MLArenaError` with `COURSE_CHALLENGE_SENTENCE` ("a challenge now belongs to its course: create it with `add_course_challenge`") and send nothing. `update_competition_link` → `update_course_challenge`, `reorder_module_competitions` → `reorder_module_challenges`.
- No other method-level alias: `update_challenge_configuration` (deprecated in 4.1.0) was removed at 4.2.0, `upload_submission_docs` / `delete_submission_docs` at 4.6.0.
- `CompetitionNotFoundError` is `ChallengeNotFoundError`. `PermissionDeniedError` subclasses `AuthenticationError`, so `except AuthenticationError` still catches a 403.

## Auth scopes

Enforced by the FastAPI dependencies of `backend/app/core/auth.py` (`require_scope` → `CurrentUser`, `AuthorUser`; a session passes both, and the object's guard decides whether a challenge or a course is the caller's); the scope set is `API_KEY_SCOPES` in `modelmanager/modelmanager/api_keys.py`, and `canonical_scope` reads a stored `creator` / `teacher` key as `author`.
- `user` — own submissions, chat as participant, enroll, course reading, own lesson progress, own credits (`credits`, `credit_usage` without an id), `create_course`.
- `author` — `/api/teacher/*`, `/api/creator_challenge/*`, the chat and exercise staff routes, `workspace()`, `credit_usage(course_id=… | challenge_id=…)`, `accept_terms()`: on the courses and challenges the user is staff of; a competition's creation and publishing need an admin besides.
- A `user` route (`CurrentUser`) takes a key of any scope; an `author` route an `author` key (or a `creator` / `teacher` one).
- An `mlo_` token acts like a key of the scope it was exchanged for; session-only (`SessionOnlyUser`) and admin (`AdminUser`) routes refuse it, as they refuse every key.
- Admins may mint every scope. Public reads (`OptionalUser`) still send the token, because `challenges`, `challenge` and `leaderboard` answer differently to an identified caller.
