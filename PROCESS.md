# mlarena-sdk — Python SDK

**Purpose**: Python client (`mlarena-sdk` 4.17.0, import `mlarena`) and the `mlarena` command over the public backend REST routes (`/api/*`).

**Key features**:
- Bearer-token auth with scope-segmented keys `mlk_<scope>_<lookup>_<secret>` (`user`, `creator`, `teacher`), or, in a GitHub Actions job, the 15-minute `mlo_<lookup>_<secret>` token of the OIDC exchange (no stored secret).
- One method per backend route, plus client-side compositions (`submit`, `status`, `tail_logs`, `resolve_runtime`, `download_dataset`, `download_replay`, `chat`, `check`, `export_course_to_dir`) that add no endpoint.
- The `mlarena` command (`whoami`, `submit`, `challenge push`, `course push`): the same methods from a shell or a workflow.
- Reads the backend's names as served (snake_case `LeaderboardRow`, `RunResult`, the submission status block); keeps no status set or key map of its own.
- Deprecated Python names from before the challenge/submission rename still resolve (published client).

**Links**: [`../ARCHITECTURE.md`](../ARCHITECTURE.md) · [`../backend/PROCESS.md`](../backend/PROCESS.md) (route groups, schemas) · [`../frontend/PROCESS.md`](../frontend/PROCESS.md) (peer consumer) · [`../CLAUDE.md`](../CLAUDE.md) (parity rule) · parity gaps: "Parity gaps" below

## Parity rule

The SDK and the React console are peers over one REST surface; every user-facing workflow is reachable from both.
- No `/api/sdk/*`, no SDK-only or frontend-only route. A route change updates `mlarena/client.py` and `frontend/src/services/*` (+ hook) in the same change.
- Auth is the only divergence: session cookie (console) vs bearer token (SDK). Route, payload and response never branch on the caller.
- SDK ergonomics are compositions of public routes, never new endpoints.

### Parity gaps (frontend-only routes, no SDK method)

- The public overview markdown / miniature reads (`GET /api/challenge_asset/*`) have no participant method; creators read them through `challenge_markdown` / `challenge_image`. Creators read the challenge configuration as `creator_challenge()["configuration"]`. Every other participant, creator and teacher route has its method (table above).
- The env-runtime image list (`GET /api/docker-kernel-version/`, the picker behind `update_settings(docker_image_env_runtime_id=…)`) has no method: the route is `auth_required("admin")`, which takes no API key, so an SDK method would only raise 403. `env_runtimes()` (machine_model §3.5) waits for that route to accept a bearer caller, or for a public read.
- By design console-only: admin cluster-ops (machines and their queues and grants — D8 —, maintenance, data-quality, admin runs, tag CRUD), the admin challenge delete (`DELETE /api/challenges/<id>`, listed in the platform CLAUDE.md), and **API-key management**. `GET /api/auth/api_keys` and `POST /api/auth/api_keys/{scope}/rotate` are `session_auth_required`: they answer 403 to a bearer caller, so that a leaked `mlk_user_…` key cannot mint a `mlk_creator_…` one for the same account. An SDK method would only ever raise 403, so there is none — `me()` covers "who am I", and keys are rotated from the console's Profile page. This is the auth axis of the parity rule, not a gap.

## Contracts

- **Runtime** (`../modelmanager/PROCESS.md` "Machines and queues") — `update_settings` carries `machine_id`, the nine sizing keys (K8s quantity strings), `number_of_agents`, and the admin-only `env_gpu_count`, `agent_gpu_count`, `gpu_memory_limit` (`_UNSET` sentinel: `None` sends null), `docker_image_env_runtime_id`. `engine_id` raises `TypeError`. `machines(kernel_version=None)` returns `MachineOut` rows as served.
- **Agent runtimes** (`../modelmanager/PROCESS.md` "Challenges") — a code challenge offers a set of agent runtime images and names a default: `update_settings(agent_runtime_ids=[…], default_agent_runtime_id=…)` (creator keys, running-editable; 400 on a foreign-kernel id, an empty set or a default outside the set), read back as `challenge()["runtime_options"]` / `["default_agent_runtime_id"]`. Each runtime has a `name`, distinct on a challenge: `submit(..., runtime="sklearn")` resolves it client-side through `resolve_runtime(cid, name)` over `runtime_options` (no route takes a name). `agent_runtimes(kernel_version)` is the catalogue the set is picked from (creator scope). `set_agent_runtime` outside the set is a 400; a deploy of a submission whose runtime left the set is a 409.
- **Challenge config** (the platform's `modelmanager/PROCESS.md` "Challenge config") — one flat document, every key the column's name = the `update_settings` keyword = the `challenge.toml` key (`config_fields()`). Two editors: `update_settings` and `challenge.toml` (applied on `upload_env_file` / `update_env_file_content` / `push_challenge` / `import_challenge_from_github`, all or nothing, errors naming lines). One owner per key: a file-owned key is a 400 from `update_settings`. `creator_challenge()["config"]` = `{values, origin, file_lines, file_applied_at_ts, file_in_sync}`. `env_max_time_per_step_second` is gone (4.3.0).
- **Data feed** — `update_settings` carries the admin-only `data_source_*` + `batch_cron` keywords (sentinel `_UNSET` = not sent, `None` = null; `data_source_filter` is `dict[str, str]`); the backend answers 403 to a non-admin. The SDK reads no feed.
- **Payload keys are the backend's exactly** (request schemas are `extra="forbid"`): e.g. `submission_name`, `copy_from_submission_id`, `copy_from_challenge_id`, `max_active_submissions_per_participant`, `challenge_id`; chat `charter_accepted`, `content`, `reason`, `llm_base_url`, `llm_model`, `llm_api_key`, `turn_timeout_sec`, `max_turns_per_session`, `max_sessions_per_participant`, `max_concurrent_turns`.
- **Submission status block** — every reply carrying a submission's `status` carries `SubmissionStatusFields` (`backend/app/views/submissions/_schemas.py`): `status`, `phase`, `last_status_message`, `status_update_ts`, `is_uploadable`, `is_deployable`, `is_settled`. `status` ∈ `SubmissionStatus` (`modelmanager/modelmanager/submissions.py`): `created`, `upload_failed`, `upload_validated`, `deploy_queue`, `deploy_run`, `deploy_failed`, `active`, `deleted`. The SDK gates on the served flags: `tail_logs` stops on `is_settled`; `submit` deploys only when `is_deployable` and returns `{"submission_id", "deploy"}`; `submit(wait=True)` returns an `active` submission or raises `SubmissionError`. `/submissions/mine` serves no `deleted` rows.
- **The submission** — `submission(sid)` is `SubmissionOut` (`backend/app/views/submissions/_schemas.py`): the status block + `id`, `challenge_id`, `submission_name`, `created_at_ts`, `is_public`, `owner`, `team`, `viewer_role` (`owner` | `teammate` | `staff` | `teacher` | `public`), `agent_runtime`, `latest_deploy` (`DeployOut`, None before the first deploy), `queue_info`, the `LeaderboardRow` numbers (`score`, `score_ci95`, `metrics`, `metrics_window`, `number_of_runs`, `last_end_run_ts`, `action_time_max_sec`, `agent_metric_*_max_bytes`) and `latest_run_failure`. Every reader reads it and its `runs` / `deploys` / files; only the owner writes (`update_submission`, uploads, deploy, delete). `tail_logs` and `submit` poll it, and `tail_logs` reads the latest attempt's runs with `submission_runs(sid, deploy_id=latest_deploy["id"])`. `list_submission_files` is metadata (`name`, `size`, `role` ∈ `entry` | `report` | `other`, `language`); a report is a `README.md` (any case) or a `.pdf`, uploaded like any file. `delete_submission` on a chat_v1 challenge is a 409.
- **Run model** — `submission_runs()["runs"]` rows are the backend's `RunResult` (`backend/app/views/run_serializers.py`): run columns (`job_status`, `job_error_type`, `job_error_message`, `job_retry_count`, `submission_deploy_id`, `env_nb_steps`, `env_error_type`, `env_error_message`, env metrics) + `submission_results` (one `RunSubmissionResult` per agent: `submission_id`, `submission_status`, the per-run columns `score`, `score_variance`, `n_episodes`, `score_ci95`, `metrics` (env keys + optional `score2`), `agent_nb_steps`, `game_outcome` (null on a solo run), `agent_error_type`, `agent_error_message`, `agent_stdout_logs`, and the footprint `agent_busy_time_sec`, `agent_call_count`, `agent_call_time_total_sec`, `agent_metric_cpu_time_total_sec`, `agent_metric_ram_gib_sec`, `agent_metric_gpu_energy_j`, `agent_metric_gpu_busy_sec`, `agent_metric_vram_max_bytes`, `agent_energy_wh`, `agent_co2e_g`; the run's env side `env_metric_ram_gib_sec`, `env_metric_gpu_energy_j`, `env_metric_gpu_busy_sec`, `env_energy_wh`, `env_co2e_g`). A null footprint value = the run was not metered; nothing in the SDK reads them as numbers. `env_error_type` / `agent_error_type` ∈ `RunErrorType` (`code_error`, `timeout`, `oom_killed`, `crash`, legacy `simulation_error`, `pod_crash`). The caller finds its own row by `submission_id`; `env_*` diagnostics are null on participant routes, `job_error_message` is served to the challenge's staff only. `latest_deploy` carries `failure_owner` (`participant` | `challenge` | `platform`). Every run row carries `replay` (`ReplayOut`: `render_format` ∈ `frames_v2` | `video_mp4` | `image_png`, `signed_url`, `render_size_bytes`; None without a replay); `replays()` / `replay()` rows are the public `ReplayRun` instead (`simulation_result_id`, `created_at_ts`, `env_nb_steps`, `replay`, `submission_results` limited to `id`, `submission_id`, `submission_name`, `user_name`, `agent_attached_player_id`, `env_player_name`, `score`, `game_outcome`, `final_rank`: the same keys, no metrics or diagnostics); `submission_runs()` and `replays()` carry `challenge_context` = `RunsContext` (`metrics`, `number_of_agents`, `render_delay_second`, the default frame duration). `download_replay` names the file `<simulation_result_id>` + the format's key suffix (`.experiment.mp`, `.frames.mp`, `.mp4`, `.png`). `run_benchmark` returns the creator's latest benchmark run in the same shape (with the env diagnostics); `benchmark_status` returns `{run, checks}` (`run` None before the first run, `checks` the config's budgets against the completed run); the backend scores the benchmark submission when the run completes.
- **Kinds** — `available_kinds()` rows carry `kernel_version` (the name every payload uses, `creator_challenge()["configuration"]` and `creator_challenges()` rows included) and closed `capabilities`: `agent_template`, `benchmark`, `env_structural_check`, `runs`, `chat`, `submission_upload`, `submission_filename`, `elo`, `episode_budget_brackets`, `run_limits`, `agent_containers`, `multi_agent`, `exercises`, `leaderboard` (False on exercise_v1: its board is hidden); plus `has_machine`, `runtime_defaults` and `runtime_presets`. The settings flags say which `update_settings` keywords a kind accepts; the backend answers 400 to the others.
- **Errors** — every refusal goes through `_handle_response` (401/403/404) or `_failed` (other codes) and carries `status_code` + `body`; no API call ends on `requests.raise_for_status()` (the presigned-R2 fetch in `download_dataset` is the one exception, pinned by `test_no_api_call_ends_on_raise_for_status`; `download_replay` raises `MLArenaError` with the storage's status code). A deploy 409 body carries `deployment_limits` and `active_submission_limits`.
- **Score model** (`../modelmanager/PROCESS.md` "Score model") — a challenge's declaration is `metrics: [MetricSpec]` (+ `window_days`), plain dicts with the ten keys `key, label, source, agg, order, format, unit, precision, is_ranking, visible` (`format` ∈ `metrics_schema.FORMATS`, `energy` / `mass` with a null `unit`; the platform keys add the footprint `energy`, `co2e`, `cpu_time`, `gpu_time`, `busy_time`, refused off flex_v1; the server validates, the SDK only documents them and formats them in `format_metric`); a submission's values are `score` + `metrics` (`{key: value}`) (+ `metrics_window`). `update_settings(metrics=…, window_days=…)` sends the whole list (`window_days=None` sends null and removes the window, `_UNSET` sentinel); the six pre-4.0.0 keywords (`metric`, `metric2`, `is_elo_score`, `metric_order`, `frontend_precision`, `metrics_schema`) raise `TypeError` naming `metrics` (`_refuses_removed_score_kwargs`, D5 — no alias). Course payloads carry `metric` (the ranking MetricSpec) + `value`.
- **Footprint** — `challenge_footprint(cid)` returns `ChallengeFootprint` as served: `{last_30d, since_start}`, each `{runs, metered_runs, agent_energy_wh, env_energy_wh, agent_co2e_g, env_co2e_g}` (Wh, g).
- **Leaderboard** — `leaderboard(challenge_id=None, top=None, *, aggregate=None, course_id=None, me=False, q=None, window=None, offset=None, around=None)` sends only the passed keys (`limit`, `offset`, `aggregate`, `course_id`, `me`, `around`, `q`, `window`); without `aggregate` the backend serves its default `user` (one row per participant), as the console asks for. The backend serves one `LeaderboardEnvelope` (`backend/app/views/_schemas.py`); the method returns its `leaders` as a DataFrame of `LeaderboardRow` with every other key (`challenge`, `total`, `me`, `around`, `matches`, `course_context`) on `df.attrs`, or the envelope dict as served without pandas. In the DataFrame (`_leaderboard_records`) each row's `metrics` becomes one column per declared key and, when `challenge.window_days` is set, `metrics_window` one `metrics_window_<key>` column per key; `df.attrs["metrics"]` is the declaration. A declared key equal to a row column raises `MLArenaError`.
- **Chat challenges** (`chat_v1`) — no upload/deploy; the team's submission is created by the first `open_chat_session` (born `active`; `create_submission` answers 409). The agent sleeps after 30 idle minutes and a read of `chat_challenge` wakes it: `wait_for_chat_agent` polls that read until `agent_online`, and `chat().say()` calls it before `open_chat_session` (which answers 409 while the agent is not online). `send_chat_message(wait=True)` sends (202 `{"turn", "message"}`) and polls `chat_session` every 0.7 s until that turn is `completed` or `failed`; its `timeout` restarts whenever the pending turn's `queue_position` (served, never derived) goes down. Money is served as two-decimal strings; only `ChatConversation.total_amount_eur` parses a `Decimal`. The group's cumulative euros and per-rule scoreboard are `participant.total_amount_eur` / `participant.scoreboard` on both the challenge view and the session view. `update_chat_settings` sends only the keywords passed (`None` clears a limit, `llm_api_key=""` clears the key; the key is never read back, only `llm_api_key_set`).
- **Exercise challenges** (`exercise_v1`) — no upload/deploy; the group's submission is created by the first attempt (born `active`; `create_submission` answers 409). `submit_exercise` sends `CreateExerciseAttemptRequest` with both keys (`code` / `answer`, the unused one null; exactly one checked client-side before any request), answers 202, and with `wait=True` polls `exercise_attempt` every 0.4 s (the console's cadence) until `passed` / `failed` (returned) or `error` (raised, attempt in `.body`); the timeout raises with the last attempt in `.body`. A 404 is `ChallengeNotFoundError` on challenge routes and `ExerciseAttemptNotFoundError` on `/attempts/{aid}`. The four limits (`time_limit_sec`, `memory_limit_mb`, `max_concurrent_attempts`, `max_attempts_per_minute`) are config keys of `update_settings` (capability `exercises`). `check()` sends `source_of(obj)` and prints `format_attempt`.
- **Credentials** (`ci_auth.py`) — one order for `connect()` and the CLI: `api_key` → `MLARENA_API_KEY` → GitHub Actions OIDC, when `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN` are both set. The exchange: `GET {request url}&audience=<audience>` with `Authorization: bearer <request token>` → `{"value": jwt}`, then `POST /api/auth/oidc/github` `{"token", "scope"}` → `{"access_token", "expires_at_ts", "username", "source_revision"}`. A 401 / 403 raises `AuthenticationError` / `PermissionDeniedError` whose message is the server's, unchanged. A key that is set but malformed raises; it is never a reason to try the next source. The client renews an exchanged token 60 s before `expires_at_ts` (`_headers`), so a `submit(wait=True)` may outlive it. CLI scopes: `submit` and `whoami` ask `user`, `challenge push` `creator`, `course push` `teacher`; an API key carries its own.
- **Bundles** — `push_challenge` / `push_course` send one multipart field `archive`: `make_bundle(dir)` (rooted at the directory; `.git`, `__pycache__`, `*.pyc`, `.DS_Store`, `.venv`, `node_modules`, `.ipynb_checkpoints` left out; a symbolic link raises), or an existing archive as it is. The server extracts, validates and applies; the client parses nothing but `course.slug` (the route's slug, when `slug=` is not given). `subpath` (CLI `--path`) is the folder inside the directory that holds the challenge or the course: for a directory both pushes bundle only that folder; for an archive `push_challenge` sends it as the route's `path` query and `push_course` raises (the course route takes none). `push_challenge` answers `ChallengeBundleResponse` (`message`, `dry_run`, `env_files`, `env_changed`, `overview_updated`, `agent_template_updated`, `image_updated`, `ignored`, `config`, `validation`, `source_revision`); `push_course` answers `CourseBundleResponse` (`dry_run`, `course`, `modules` with `lessons` / `orphaned_lessons` / `pruned_lessons` / `assets`, `unmanaged_modules`, `source_revision`, `url`). A 200 whose `validation.ok` is false is an applied bundle with a broken `env.py`: the CLI prints the errors and exits 1.
- **Same commit** — a submission created by an `mlo_` token records the run's commit (`submission()["source_revision"]`). `create_submission` sends `allow_same_commit` only when true; the second create of a commit is a 409 `SubmissionError` with `body["submission_id"]`. `submit` turns that 409 into `{"submission_id", "deploy": None, "already_submitted": True, "status": submission()}`; any other 409 propagates. `submit(deploy=False)` returns `{"submission_id", "deploy": None}` after the upload check.
- **Course manifest** — the format is the server's (`backend/app/services/course_manifest.py`): `course` (`name`, `slug`, `code`, `description`, `visibility`, `instructor_name`, `start_date`, `end_date`, `cover`) and `modules` (`title`, `slug`, `renamed_from`, `summary`, `icon`, `visibility`, `is_published`, `challenges` of `{slug | challenge_id, label, pass_threshold}`, `lessons` of `{title, slug, renamed_from, kind, file | body_md, gated, is_published, estimated_minutes, children}`); every path and every relative link of a lesson body is relative to the course root; unknown keys are refused; `competitions:` / `competition_id:` are permanent input aliases the server reads (CLAUDE.md, "Vocabulary"). `export_course_to_dir` writes exactly those keys, so its output pushes back unchanged: lesson bodies at `<module>/<lesson>.md`, nested lessons as `children` (from `parent_lesson_id`), a challenge by `slug` when `challenge.slug` is set (else `challenge_id`), the module's `visibility` from `get_module` when the landing says `can_manage`, the cover as `cover.<ext>` from the served content type, and each relative link of a body (the server's own link rule, mirrored in `_relative_asset_links`) fetched from the lesson's `asset_base_url` to the same path from the root. A linked file that is a 404 warns and is skipped; two modules holding different files under one path raise.
- **Module assets** — a module has one asset store; a lesson body links a file by its path in it (`![](media/fig.png)`), resolved against `lesson()["asset_base_url"]`. `upload_module_asset` sends multipart `file` + form field `path` (default on the server: `media/<file name>`) and returns `{path, url}`; `list_module_assets` rows add `size_bytes`. A module with `content_origin == "bundle"` refuses editor writes (409) until `detach_module`.
- **Course payload names** — a course object carries `has_cover` (never the stored `cover_image_path`: the catalog and the landing are public reads and an NFS path would publish the share's layout) and the client builds the image URL from the course id (`course_cover` / `courseCoverUrl`); a module object is keyed `id` and a link object carries `module_id`/`challenge`; an enrollment row is keyed `user_id` and dated `enrolled_at_ts`; the enroll-info payload nests the course under `course`. A course's module row carries `layout` (`simple` | `advanced`) — the platform's own rule, not a client guess.

## Deprecated aliases (frozen — CLAUDE.md, "Vocabulary")

- `_RENAMED_METHODS`: old method names (`competitions`, `create_competition`, `deploy_agent`, `agent_games`, `submission_games`, …) warn (`DeprecationWarning`) and call the new method. `_KEYED_BY_SUBMISSION_METHODS` (`agent_status`, `submission_status`, `submission_overview` → `submission`) do the same and drop the old leading `challenge_id`. The module raises at import if a target method is missing.
- `_LEGACY_KWARGS`: old keyword names (`competition_id`, `agent_id`, `agent_name`, …) are accepted on every public method; passing both spellings raises `TypeError`.
- No other method-level alias: `update_challenge_configuration` (deprecated in 4.1.0) was removed at 4.2.0, `upload_submission_docs` / `delete_submission_docs` at 4.6.0.
- `CompetitionNotFoundError` is `ChallengeNotFoundError`. `PermissionDeniedError` subclasses `AuthenticationError`, so `except AuthenticationError` still catches a 403.

## Auth scopes

Enforced by `auth_required` / `user_satisfies_scope` in `backend/app/auth/decorators.py`; the scope set is `API_KEY_SCOPES` in `modelmanager/modelmanager/api_keys.py`.
- `user` — own submissions, chat as participant, enroll, course reading and own lesson progress.
- `creator` — `/api/creator_challenge/*` and the chat creator routes, on challenges the user owns or assists.
- `teacher` — `/api/teacher/*` and `create_course`.
- An `mlo_` token acts like a key of the scope it was exchanged for; session-only and admin routes refuse it.
- Admins may mint every scope. `@login_required` routes accept any bearer token (Flask-Login `request_loader` → `load_user_from_request`). Public reads still send the token, because `challenges`, `challenge` and `leaderboard` answer differently to an identified caller.

pip install -e mlarena-sdk                                  # Python >= 3.10; requests + pyyaml; pandas optional ([pandas] extra), video replays in record_render ([video] extra)
backend/.venv/bin/python -m pytest mlarena-sdk/tests -q     # offline unit tests (pytest, requests, pandas)

MLARENA_API_KEY=mlk_… MLARENA_BASE_URL=http://localhost:4999 mlarena whoami   # or: python -m mlarena.cli whoami

The local backend is `http://localhost:4999` (`kubectl port-forward svc/backend 4999:4999`); seeded deterministic keys are in `tests-dummy/.dummy-keys.json` ([`../tests-dummy/README.md`](../tests-dummy/README.md)). Locally the OIDC audience is the console's URL, not the API's: `MLARENA_OIDC_AUDIENCE=http://localhost:3000` (the backend's `PUBLIC_BASE_URL`). `mlarena-sdk/` is its own repository (gitignored here); its `README.md` is the user-facing reference.
